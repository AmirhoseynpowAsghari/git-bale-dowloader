# GitHub → Bale Downloader

ربات دانلود ریپازیتوری عمومی GitHub و ارسال فایل ZIP به گفت‌وگوی خصوصی یا گروه در بله. بعد از دانلود، کاربر انتخاب می‌کند که **فقط دانلود** انجام شود یا **آپدیت‌های بعدی** هم ارسال شوند. اجرای ربات با GitHub Actions است و به سرور جداگانه نیاز ندارد.

## Button fixes in this version

Both inline buttons and their text-button fallbacks are handled:

- **نه فقط دانلود** / **نه، فقط دانلود** → automatic updates stay disabled.
- **بله آپدیت هارو بفرست** / **بله، آپدیت‌ها رو بفرست** → automatic updates are enabled.
- Existing `f:1:…` and `f:0:…` buttons remain compatible.
- `بله`، `خیر`، `yes` and `no` also work for the current question.

The original code acknowledged every callback before executing its action. Bale documents that older clients do not support `answerCallbackQuery`; an acknowledgement failure could therefore prevent the choice from being saved. This version skips unsupported legacy acknowledgements, treats other acknowledgement errors as non-fatal, and still executes the button action. It also provides ordinary reply-keyboard buttons as a fallback. See the [official Bale API documentation](https://docs.bale.ai/).

> **زمان پاسخ‌گویی:** این نسخه وب‌هوک یا سرور همیشه‌روشن ندارد. دکمه‌ها در اجرای بعدی Actions پردازش می‌شوند. زمان‌بندی هر ۵ دقیقه درخواست می‌شود، ولی GitHub ممکن است آن را با تأخیر اجرا کند؛ پاسخ فوری تضمین نمی‌شود.

## ۱) راه‌اندازی ربات بله

1. در [@botfather](https://ble.ir/botfather) ربات بسازید و توکن را محرمانه نگه دارید.
2. برای گفت‌وگوی خصوصی، ربات را شروع کنید. برای گروه، ربات را اضافه کنید و اجازه ارسال پیام و فایل بدهید.
3. در ریپازیتوری میزبان، وارد **Settings → Secrets and variables → Actions** شوید.
4. در **Secrets** فقط مقدار `BALE_BOT_TOKEN` را تنظیم کنید. `GITHUB_TOKEN` و اطلاعات ریپازیتوری میزبان را GitHub Actions فراهم می‌کند.
5. فایل‌های این نسخه را به **شاخه پیش‌فرض** ریپازیتوری منتقل کنید؛ زمان‌بندی workflow از شاخه پیش‌فرض اجرا می‌شود.
6. در **Actions** اجرای ربات را فعال کنید، سپس **Interactive Bale GitHub Downloader → Run workflow** را بزنید.
7. در بله `/start` و بعد لینک اصلی ریپازیتوری را بفرستید، مثلاً `https://github.com/octocat/Hello-World`.

`BALE_CHAT_ID` لازم نیست؛ شناسه هر گفتگو از پیام دریافت می‌شود. اگر این Secret از نسخه قبلی باقی مانده، کد جدید از آن استفاده نمی‌کند.

### وب‌هوک قبلی

`getUpdates` و وب‌هوک هم‌زمان کار نمی‌کنند. ربات وضعیت وب‌هوک را بررسی می‌کند و بدون اجازه آن را حذف نمی‌کند. اگر لاگ می‌گوید `A Bale webhook is active`، وب‌هوک را خودتان غیرفعال کنید؛ یا اگر این ربات باید جایگزین اتصال قبلی شود:

1. در **Settings → Secrets and variables → Actions → Variables** مقدار `BALE_RESET_WEBHOOK` را `true` قرار دهید.
2. workflow را دستی اجرا کنید.
3. پس از موفقیت، متغیر را `false` کنید یا حذف کنید.

حذف وب‌هوک با `drop_pending_updates=false` انجام می‌شود. پیام‌هایی که در زمان فعال‌بودن وب‌هوک به آن تحویل شده‌اند، لزوماً در صف polling نیستند؛ بعد از تغییر روش، لینک را دوباره بفرستید.

## ۲) دستورها و دکمه‌ها

| دستور / انتخاب | عملکرد |
|---|---|
| `/start` یا `/help` | راهنما |
| `https://github.com/owner/repo` | دانلود ZIP نسخه فعلی شاخه پیش‌فرض |
| `نه فقط دانلود` | ثبت حالت فقط دانلود، بدون اشتراک آپدیت |
| `بله آپدیت هارو بفرست` | فعال‌کردن ارسال تغییرات بعدی |
| `/list` یا `/status` | نمایش وضعیت هر ریپازیتوری |
| `/stop owner/repo` | حذف ریپازیتوری از فهرست و توقف آپدیت |
| `/cancel` | بستن سؤال باز و فعال‌نکردن آپدیت |

در گروه، فقط کاربری که لینک را فرستاده می‌تواند انتخاب آپدیت را ثبت یا اشتراک را متوقف کند. دکمه‌های پایین صفحه برای سازگاری بیشتر ارسال می‌شوند و پس از انتخاب حذف می‌شوند. انتخاب تکراری، اشتراک دوم یا پیام تأیید اضافی ایجاد نمی‌کند.

ارسال دوباره لینک یک ریپازیتوری فعال، نسخه کامل جدید را می‌فرستد و اشتراک آن را خاموش نمی‌کند.

## ۳) آپدیت‌ها چگونه ارسال می‌شوند؟

- در اولین دانلود، snapshot فایل‌ها و commit ذخیره می‌شود؛ فایل‌های قدیمی به‌عنوان آپدیت ارسال نمی‌شوند.
- در بررسی بعدی، فقط محتوای فایل‌های جدید یا تغییرکرده در ZIP آپدیت قرار می‌گیرد.
- فایل حذف‌شده یا تغییرنام‌یافته در گزارش می‌آید؛ فایل حذف‌شده از دستگاه کاربر پاک نمی‌شود.
- ZIP آپدیت یک استخراج مستقل است، نه patch قابل اعمال با Git. فایل‌ها را در محل پروژه خود کپی کنید.
- اگر فقط فایل حذف شده باشد، گزارش متنی ارسال می‌شود.
- تغییر صرفاً در پیام commit، بدون تغییر فایل، ZIP ایجاد نمی‌کند.
- هر گفتگو حداکثر ۵ ریپازیتوری ثبت‌شده دارد.

## ۴) ساختار کد

```text
bot.py                         # ورودی سازگار با نسخه قبلی
bale_downloader/
  __main__.py                  # اجرای یک چرخه polling و تحویل آپدیت
  config.py                    # تنظیمات و محدودیت‌ها
  bot.py                       # دستورها، دکمه‌ها و اشتراک‌ها
  bale.py                      # API بله، سازگاری کلاینت قدیمی و خطاهای امن
  github.py                    # snapshot و دانلود ZIP عمومی GitHub
  storage.py                   # وضعیت رمزگذاری‌شده روی شاخه جداگانه
  models.py                    # ساختار وضعیت و مهاجرت نسخه قبلی
  ui.py                        # دکمه‌ها و تجزیه پاسخ فارسی/انگلیسی
  archives.py                  # اعتبارسنجی لینک و ساخت ZIP تغییرات
  errors.py                    # خطاهای قابل نمایش
.github/workflows/
  bale-watcher.yml             # اجرای زمان‌بندی‌شده پس از lint و test
  tests.yml                    # بررسی خودکار push و pull request
tests/                         # تست‌های بدون نیاز به توکن یا شبکه
```

پوشه workflow تکراری و غیرفعال `github/workflows/` حذف شده است. تست قبلی ماژول موجودنبودِ `watcher` را import می‌کرد؛ تست‌های جدید ماژول‌های واقعی این پروژه را پوشش می‌دهند.

## ۵) وضعیت و امنیت

وضعیت در `state.enc` روی شاخه `bale-interactive-state` ذخیره می‌شود. این شاخه را حذف نکنید. اطلاعات با کلید مشتق از توکن ربات رمزگذاری می‌شوند؛ **توکن را عوض نکنید مگر اینکه برای راه‌اندازی مجدد وضعیت آماده باشید**. وضعیت نسخه قبلی در اولین بارگذاری به ساختار نسخه ۲ مهاجرت می‌کند.

- توکن‌ها در کد، لاگ یا فایل نمونه ذخیره نمی‌شوند.
- خطاهای شبکه، URL حاوی توکن را نمایش نمی‌دهند.
- ذخیره وضعیت از blob SHA برای جلوگیری از بازنویسی هم‌زمان استفاده می‌کند.
- انتخاب کاربر قبل از ارسال پیام تأیید ذخیره می‌شود.
- offset فقط پس از پردازش موفق پیام جلو می‌رود.
- وضعیت خراب یا قابل رمزگشایی‌نبودن با وضعیت خالی جایگزین نمی‌شود.
- مسیرهای آرشیو و حجم دانلود/استخراج محدود شده‌اند.
- دسترسی نوشتن `GITHUB_TOKEN` فقط برای شاخه وضعیتِ ریپازیتوری میزبان استفاده می‌شود؛ هدف‌های دانلود عمومی هستند.

## ۶) اجرای تست‌ها

Python 3.11 یا جدیدتر:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m ruff check .
python -m ruff format --check .
python -m pytest -q
```

تست‌ها شامل هر دو دکمه، متن‌های درخواستی، کلاینت قدیمی، کلیک تکراری، مجوز گروه، ذخیره انتخاب، شکست شبکه، مهاجرت وضعیت، ساخت ZIP و ارسال آپدیت هستند. تست‌ها به API واقعی پیام نمی‌فرستند.

ورودی `python bot.py` همچنان پشتیبانی می‌شود. برای اجرای محلی واقعی، متغیرهای محیطی معتبر لازم‌اند؛ `.env.example` فقط فهرست متغیرهاست و خودکار بارگذاری نمی‌شود. اجرای محلی وضعیت واقعی را تغییر می‌دهد؛ برای آزمایش از تست‌ها استفاده کنید.

## ۷) محدودیت‌ها و عیب‌یابی

- مجموع محتوای فایل‌های snapshot حداکثر **۵۰٬۰۰۰٬۰۰۰ بایت** و هر ZIP حداکثر **۴۸٬۰۰۰٬۰۰۰ بایت** است. این محدودیت محافظه‌کارانه برای سقف اعلام‌شده ۵۰ MB بله است، نه تضمین پذیرش هر فایل توسط API.
- فقط ریپازیتوری عمومی و شاخه پیش‌فرض پشتیبانی می‌شود. تاریخچه Git، فایل واقعی LFS و submodule بازیابی نمی‌شوند.
- در هر اجرا حداکثر ۳۰۰ پیام در ۳ دسته پردازش می‌شود. پیام‌های باقی‌مانده در اجرای بعدی بررسی می‌شوند.
- GitHub ممکن است اجرای زمان‌بندی‌شده را به تأخیر بیندازد یا در ریپازیتوری عمومی بی‌فعالیت پس از ۶۰ روز غیرفعال کند.
- اگر دکمه پاسخ نمی‌دهد، موفق‌بودن اجرای Actions، تنظیم‌نبودن وب‌هوک، عضویت/مجوز ربات و درست‌بودن توکن را بررسی کنید. بعد از ارتقا، یک لینک جدید بفرستید تا دکمه‌های جدید و fallback ایجاد شوند.
- اگر خطای ذخیره وضعیت دارید، دسترسی `contents: write`، محدودیت‌های سازمان و محافظت شاخه را بررسی کنید.
- ارسال کاملاً exactly-once ممکن نیست: اگر ارسال موفق شود ولی ذخیره وضعیت یا offset شکست بخورد، اجرای بعدی ممکن است فایل یا تأیید را تکرار کند. انتخاب اشتراک تکراری، وضعیت را خراب نمی‌کند.

**اعتبارسنجی این تغییرات:** تست‌های خودکار و lint اجرا شده‌اند. اجرای واقعی داخل حساب بله شما نیاز به توکن و اجرای workflow دارد؛ بدون آن، تحویل واقعی پیام/فایل تأیید نشده است.
